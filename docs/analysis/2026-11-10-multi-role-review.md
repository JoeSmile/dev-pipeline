# 多角色需求复查（2026-11-10）

对照：`README.md`、`docs/CHARTER.md`、`docs/architecture/dev-pipeline.md`，以及 Jira `DP-1`～`DP-25`。角色按 CHARTER 第 6 节：交付编排、产品/业务、架构、实现、真实用户、UX。本文是立项复查，不是已拍板方案。

## 结论

主路径已经拆全：状态机、人工 Signal、幂等键、Jira 镜像、范围/方案/Spike、写码沙箱、双 Review、HumanGate、验证证据、Retro 与禁止静默升级。这些票「有题目」，但多数验收仍偏原则，还不够当成实现契约。

真正会卡住实现的，不是漏了一两个小功能，而是下面三类结构性缺口。不先拍板，后面每张实现票都会各写各的。

1. **编排粒度未锁**：`Intake`～`TicketsReady` 是 Story 级，`Implementing`～`Verifying` 是 Ticket 级，`Retro` 又像 Story 级（还和每日复盘文件重叠）。当前没有一张票写清：一条 `DevPipelineWorkflow` 管整张 Story，还是每张 Ticket 一条 Child；多票串行还是按依赖并行；一张失败是否挡住同 Story 其他票。
2. **人怎么操作、怎么看见，没有票**：Signal 名单有了，但没有操作入口（CLI / Temporal UI 抄什么）、没有 Query（当前阶段、在等哪个 Signal、预算花了多少）、没有「等人时系统给出可抄状态、但不催人」的约定。这和全局优先级里的「可观测与可回放」「人工门禁清楚」对不上。
3. **CHARTER 已写、票上未落地的硬约束**：默认不自动 push、不自动合并、不自动改全局规则；单次失败不得破坏其他工作区或已合并主线；中止/重开后的扫尾与产物继承。这些会改变写码与 Review 的验收，不能只留在宪法草稿里。

RAG、开发环境初始化、配置根目录与密钥、证据落盘格式，属于能力缺口，建议补票，但优先级低于上面三条。

## 建议先拍的 4 件事

未拍之前，加细现有票只能写到「待证」，不能假装已齐。

1. 一条父 Workflow 对应一张 Story；每张实现 Ticket 用 Child（或等价的可独立幂等执行）。多 Ticket 默认按依赖拓扑执行；无依赖可并行；单张失败不自动取消同 Story 其他未受影响的 Ticket，但 Story 不能进 Retro，直到失败被处理或人工 `abort`。
2. 本期无人产品界面。人通过本仓库 CLI 发 Signal、查状态；可用 Temporal UI 对照 History。Jira 只镜像，不当操作台。
3. 默认不自动 `push`、不自动合并、不自动改全局规则。开 PR 必须另有明确授权；未授权则只在授权 worktree 产生产物。
4. `abort` 必须留下可回放记录，并回收本 execution 创建的未合并分支 / worktree；已存在的远程 PR 不得偷偷关闭或合并，只标记并等待人工处理（具体动作待证）。`reopen` 开新 `execution_id`，可继承只读产物（范围、方案、假设、已关闭的 Ticket 证据），不得复用已乱掉的工作区。

## 各角色意见

### 交付编排

拆票覆盖了 README 状态机，没有明显「整段阶段没票」。缺口在验收门禁和依赖写法。

- 多张票互相写「依赖某某 Story」，但 Story 级编排规则本身没有票，依赖会悬空。
- `DP-10` 对未到阶段的 Signal 写「拒或明确忽略」，两个行为必须定一个，否则验收无法判。
- 后期人验仍应只认 README 里可抄命令；本期至少要有「操作入口 + 状态查询」票，否则以后会再走一遍临场三行催测。
- 交付方必须能自跑出证据。现在没有「最小可自验路径」（本地 Temporal、假 Worker、状态转移、Signal、镜像失败）这张票。

### 产品 / 业务

用户要的是「从一张诉求到可复现交付 + 知识回流」，不是单独的状态枚举。业务上还缺这些可验收行为：

- 启动：谁、用什么命令或 Jira 动作拉起一条 Story 执行；启动失败必须显式失败（`DP-13` 已提，但触发方式仍待证）。
- 等待人工时：系统进入明确等候，不自行猜测范围或方案，也不把等候当成失败。
- 一张 Story 拆出多张实现 Ticket 后，业务完成条件是「全部必做 Ticket 过验证」，不是「某一张过了就进 Retro」。
- Blocked / 否决后，对人的业务结果是什么：Jira 上看得到、执行已停止、不继续计费。现在只有阶段名。
- 每日复盘（`docs/knowledge/daily/YYYY-MM-DD.md`）和 Story 末尾 Retro 的关系没写清。建议：Story Retro 把本 Story 证据追加进当天 daily，并更新 candidate；它不替代日终复盘 Skill，也不允许把 Retro 写成难度打分日报。
- candidate 升级条件（真实命中 N≥2 或一次硬近失，且必须 `promote_rule`）写在个人工作习惯里，尚未写入 `DP-25` 验收。
- RAG 出现在阶段契约的输入里，但没有任何业务票定义「检索什么、命中什么算有效、检索失败时是否允许仅靠已锁范围继续」。

非目标仍应保持：本期不对接近 `agent-platform`、不做产品 UI、不把 Jira 当编排器、不自动升级 L0。

### 架构

父 Workflow 保持确定性，这个方向对。需要补模块边界，否则 Child / Activity 会挤成一团。

- 建议模块：状态机与 Signal、Jira 适配（单向镜像 + 可选开单）、预算账本、Git/worktree 适配、Coding Child、Review Child（只读）、Verifying、Retro / 知识回流、配置与密钥（不进 History）。
- 必须有 Query：当前阶段、等待中的 Signal、Ticket 清单与各 Ticket 子状态、已耗预算、最近一次失败原因。Query 只读，不改变状态。
- 预算：计量口径（token / 调用次数 / 费用，至少先定一种可配置单位）、账本存在哪、超限后哪些路径立刻不可用。限额数值可继续待证，口径不能待证。
- 双 Review 分歧：一人阻断、一人仅建议时，按「有阻断或范式漂移就必须 HumanGate」已经可判；但两条都阻断且理由冲突时，仍进 HumanGate，由人裁，Workflow 不做自动仲裁。这一点应写进 `DP-22` / `DP-23`。
- Jira 镜像失败：重试、死信、以 History 为真相、票上能看到「镜像滞后」。字段名可待证，失败策略不能待证。
- Workflow 版本与 Signal 载荷要有显式 schema（字段、必填、拒绝条件）。`reopen` 与幂等键的关系：新 execution 新键；旧 execution 不得被继跑。
- L0 在执行中被改：进行中的 execution 继续使用启动时冻结的 L0 快照，还是下次门禁才读新版，必须先定（建议：启动时快照，改宪不影响已跑实例，除非人工 `abort` 后 reopen）。

### 实现

现在没有「能跑起来」的地基票，直接做 `DP-9` 会缺测试夹具。

- 建议补：开发环境初始化（Python 3.12、Temporal 本地、本仓库 Worker 进程、配置根目录）。配置根目录必须是显式参数，缺了就失败，不得吞成「可能已存在」。
- 建议补：操作 CLI（至少：启动、发 Signal、查状态 / Query）。命令进 README 的时间可以晚于实现，但票要先有。
- 建议补：证据落盘契约（路径、编码 UTF-8、一份「红线 ↔ 证据」记录的最小字段）。Windows 本机是第一运行环境，路径与控制台编码必须作为验收条件，不能事后再补。
- `DP-20` / `DP-21` 要写清：分支命名、worktree 生命周期、测试在哪个树里跑、对远程仓库的写权限默认关闭。
- 最小自验：用桩 Activity 跑完「无 Spike、无阻断、验证过线、Retro 写文件」以及「未 lock_scope 不能编码」「超预算即停」「镜像失败不改 History」几条。没有这组测试，状态机票不能算可验收。

### 真实用户 / UX

第一用户是单人总设计师，AI 是研讨与执行伙伴。人只想在门禁点出现，并且门禁要短、可抄、可回放。

- 每个等候点应能用一条命令看到：现在停在哪、要他拍什么、用哪条命令拍、不拍会怎样（继续等，不超时自动放行，除非另拍超时策略）。
- 不要做催办通知；可以在 `status` 里显示等候时长，由他主动来看。
- 打回、否决、中止的用语要和状态机一致，避免「关了会话但票还在跑」这类含糊结果。
- 本期不需要产品 UI；Temporal UI 只作 History 对照，不作为唯一操作方式。

## 建议新开的票

挂到现有 Epic，不新开 Epic。`DP-7` 仍不拆实现。

1. **Story 父执行与 Ticket Child 编排**（DP-1）：粒度、依赖、并行、单张失败、何时允许 Story 进 Retro。这是实现的第一张设计票，建议排在 `DP-9` 之前或与之合并后重写 `DP-9`。
2. **Query 与等候点可观测**（DP-1）：当前阶段、等待 Signal、预算、失败原因；只读。
3. **操作 CLI：启动、Signal、状态**（DP-1）：无人界面前提下的人机入口；失败不得吞。
4. **开发环境与配置根目录**（DP-1）：本地 Temporal、Worker 进程、显式配置根；缺配置即失败。
5. **中止/重开扫尾与产物继承**（DP-1）：落实 `abort` / `reopen` 对分支、worktree、未合并 PR、只读产物的处理。可从 `DP-10` / `DP-11` 拆出，避免那两张票过载。
6. **默认不自动 push / 合并**（DP-4）：把 CHARTER 爆炸半径写成写码验收；若要开 PR，另写授权条件。
7. **证据落盘格式与编码**（DP-6）：路径、UTF-8、最小字段、Windows 控制台编码。
8. **RAG 检索边界**（DP-3，可后置）：检索范围、失败降级、预算记账；未做前，`decide_scheme` 允许用桩，但要在票上标明。

可选、建议标本期 OOS：Jira webhook 自动拉起、产品 UI、通知/催办、自动关 PR、对接 `agent-platform`、超时自动放行门禁。

- 在 Jira 自动化里驱动阶段跳转。
- 给 Codex / Cursor 再做一套与状态机平行的任务清单（`TASKS.md`）。
- 把日终复盘 Skill 搬进 Workflow 里替换 `DP-25`。二者配合，不互替。
