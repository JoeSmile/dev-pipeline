# DP-26 决策记录

本记录固化 [DP-26](https://weiperfect007.atlassian.net/browse/DP-26) 的编排粒度。一条父 `DevPipelineWorkflow` 对应一张 Story；每张实现 Ticket 用独立、可幂等的 Child（`TicketWorkflow`），或等价的可独立幂等执行。幂等键仍是 `ticket_id + execution_id`（`ticket_workflow_id`，同时用作 Child workflow id），见 [DP-11](https://weiperfect007.atlassian.net/browse/DP-11)。父执行 id 仍是 `story_workflow_id(story_id, execution_id)`。不另做第二套父 / Child 模型，不引入「可延后 Ticket」类型，不在本票实现或改写 Coding / Review / Verifying / Retro 产品逻辑，也不产品化已锁定名称的 `TestDeploying` 桩。

## 依赖拓扑与并行

清单齐后，父执行进入聚合 `Implementing`，并为每张必做 Ticket 建立 Child。多 Ticket 默认按依赖拓扑执行：无未完成依赖的 Ticket 可并行进入 `Implementing`；依赖未过线的 Child 保持 `Pending`，不得提前开工。即使 Child 被直接启动且声明了未过线依赖，也停在 `Pending`。快照上 `child_created` 表示 Child 已建立，`started` 表示已获准开始工作。父编排等候下一张可开工 Ticket 时，不只看 `ticket_event`：依赖已过线的 Child 即使唤醒标志已被清除，也必须被重新评估并开工，不能停在 `Pending`。

## 单张失败与 Retro 门禁

单张 Child 失败（实现失败进入 `Failed`、验证未过线打回 `Implementing`、或 `review_override` 否决进入 `Blocked`）不自动取消同 Story 其他未受影响的 Ticket。父执行保持聚合 `Implementing`，不得进入 `TestDeploying` 或 `Retro`，直到该失败被处理。全部未移除的必做 Ticket 验证过线后，才允许走既有授权与 `TestDeploying` 桩进入 `Retro`（见 [DP-25](https://weiperfect007.atlassian.net/browse/DP-25)）。被 `drop_ticket` 移除的 Ticket 不再阻挡。

## 失败处理路径

不另开第二套放弃或改清单机制。现有 Signal 已覆盖票面要求的三条路径：

1. **打回重做**：`review_override` 打回，或 Verifying 未守住红线，只让该 Ticket Child 回到 `Implementing`。已 `Failed` 或否决后停在 `Blocked` 的票，用同一次执行内的 `retry_ticket` 再进入 `Implementing`，不分配新的 `execution_id`。
2. **人工放弃并改清单**：`drop_ticket` 把该票从必做清单移除。`submit_tickets` 只用于 `TicketsReady` 补齐清单；清单齐后不能再用它改写清单。
3. **`abort`**：中止整条 Story，向仍在运行的 Child 发送 `abort` 并取消它们，再以可回放结果进入 `Blocked`。这是人工处理整条 Story 的路径，不是单张失败后的自动取消。

## 非目标与待证

不引入「可延后 Ticket」。不产品化 `TestDeploying`。`reopen` 对审查裁决、验证记录、Retro / 晋升记录，以及已提交清单 / Child 的继承仍为待证，本票不发明继承规则。超时策略对审查裁决的继承仍为待证。

## 验收与测试

文档与测试均体现：父执行=Story，Child=实现 Ticket。单元、拓扑与 WorkflowEnvironment 测试证明：无依赖的两张 Ticket 可并行开工；有依赖时后一张保持 `Pending`、不得抢跑；一张 Child 失败时同胞不自动取消，`authorize_test_deploy` 被拒绝，父执行不能进 Retro；全部必做票过验证后才允许 Retro。现场 History 打在已运行的官方 Temporal（`TEMPORAL_TARGET`，例如 `host.docker.internal:7233`），覆盖并行与依赖，以及单张失败不取消同胞、处理前不得进 Retro；使用临时树和假 Jira，不起临时 Temporal 服务，不写真实 Jira 票，不调用现场 Cursor CLI。业务阶段若未结束，断言后 `abort`；不 terminate 已完成的 Workflow，也不 `await handle.result()` 把业务 Done 误写成 Temporal COMPLETED。
