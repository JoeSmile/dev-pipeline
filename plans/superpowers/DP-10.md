# DP-10 决策记录

本记录固化 [DP-10](https://weiperfect007.atlassian.net/browse/DP-10) 人工 Signal 与 reopen 新 execution 的主流做法。不扩展范围：不实现业务 Activity 细节，不处理 abort/reopen 对分支、worktree、PR 的扫尾（见 [DP-30](https://weiperfect007.atlassian.net/browse/DP-30)）。

## 拒绝必须显式，不得忽略

错误阶段或非法 payload 的 Signal 一律拒绝：写入可查询的 `last_rejection`（signal 名 + 中文原因），并同步 `last_illegal` 以兼容既有查询。拒绝不改变当前阶段。Signal 处理函数不得抛错以免打断 Workflow。

为避免 Temporal 按类型提示反序列化失败后直接丢弃 Signal，处理函数的参数注解为 `Any`，再在进程内用 `signal_schemas.parse_human_signal` 校验。

## Payload schema 一律显式

每个人工 Signal（含 `authorize_test_deploy`）都有 dataclass 与必填字段定义，见 `src/dev_pipeline/signal_schemas.py` 与 README 表格。`approve_spike` / `abort` / `reopen` 不再接受裸 `bool` 或裸字符串。

`decide_scheme` 只在 `ScopeLocked` 合法；`approve_spike` 只在 `Spike` 合法。这与合法转移表一致，不再提前在 Intake 收下方案或 Spike 决定。

## promote_rule 区分两种拒绝

- schema / 类型错误：Signal 被拒绝，记入 `last_rejection`，阶段不变。
- `automatic=true`：Signal 已接收且可见，但晋升动作被拒绝并记入 `promote_rule_status` / `last_illegal`（L0：禁止静默升级）。这不是「忽略 Signal」。

## reopen 只在终态启动全新父执行

- 仅当当前父执行已处于 `Blocked` 或 `Done` 时接受 `reopen`。仍在运行时拒绝，调用方须先 `abort`。拒绝不改变阶段。
- payload 必须带非空且不同于当前的 `execution_id`，否则拒绝。
- 接受后通过 Activity `start_reopened_workflow`（显式 30s timeout、最多 3 次重试）用 Temporal Client 启动一条**新的、独立的** `DevPipelineWorkflow`。workflow id 为 `story_workflow_id(story_id, new_execution_id)`。启动载荷只含 story 身份与作为路径的 `config_root`，不含密钥。
- 不使用 Continue-As-New（那会复用本次 execution）。不把新执行当成会随父关闭而结束的普通 Child。
- 成功后旧执行保持原终态，快照记录 `reopened_execution_id`，然后 Temporal 工作流才结束。目标 workflow id 已存在时返回中文错误，不恢复旧执行，也不静默成功。
- 父执行进入业务终态后会短暂停住以接收 `reopen`；未 reopen 的执行可查询快照，不必等待 `result()`。

## 测试与 Docker

单元与门禁测试优先使用 `temporalio.testing.WorkflowEnvironment`，并拉取 History 断言 Signal 名与 reopen Activity。真实 Temporal History 验收由 `tests/test_signal_history_live.py` 承担，需设置 `TEMPORAL_TARGET`。Docker 用法见 `docs/dev-setup.md`。
