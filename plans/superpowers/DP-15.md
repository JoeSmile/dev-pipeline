# DP-15 决策记录

本记录固化 [DP-15](https://weiperfect007.atlassian.net/browse/DP-15) 把原始 Intake 诉求整理成规范化 Story 草稿的主流做法。不扩展范围：不在本票执行 `lock_scope` 或离开 Intake，不拍技术方案，不开启编码 / 派 Child，不把 Cursor CLI 接成现场模型调用。

## 草稿形状

引入可序列化的 `StoryDraft`，作为后续 [DP-16](https://weiperfect007.atlassian.net/browse/DP-16) `lock_scope` 的输入，挂在现有父执行 Query `snapshot.story_draft` 上，不另开第二套 Query。草稿至少包含：

- `to_solve`（要解决什么）
- `known_constraints`（已知约束）
- `missing_items`（缺项列表）
- 一并给出 `out_of_scope`（不做什么）和 `acceptance`（验收），供 `lock_scope` 对照，但本票不锁范围

缺项一律标 `待证`，不得默填，也不得把仍有缺项的草稿标成已齐（`complete=False`）。禁止臆造验收：只有原始诉求里用显式标签写出的验收才可写入 `acceptance`，否则该字段为 `待证` 并进入缺项列表。

`lock_scope` 的 `in_scope` / `out_of_scope` 分别对应草稿的 `to_solve` / `out_of_scope`。本票只提供预览帮助函数，不发送该 Signal，也不因草稿有缺项而改现有 Signal 行为。

## 如何整理

规范化是纯函数 `draft_story_from_intake`，由 Activity `normalize_story_draft` 调用，以便以后把可能的模型 / Cursor CLI I/O 留在 Activity，Workflow 保持确定性。

- 原始诉求（`intake.request`）是第一来源；仅当诉求缺失或已是 `待证` 时，才回退到 `StoryInput.summary`。
- 若诉求中带有显式中文标签（`要解决什么` / `要解决`、`已知约束`、`不做什么`、`验收` / `验收标准` / `验收条件`，且带 `:` 或 `：`），只摘录标签后的原文，不改写、不补全。
- 无标签的整段诉求只填入 `要解决什么`；不得从散文中推断约束或验收。
- 空白或字面 `待证` 视为缺项。

本票默认走确定性后端，不读取 `CURSOR_API_KEY`，不调用 Cursor CLI，也不假装已做过现场模型调用。预留 `CursorCliStoryDraftBackend` 接口，本票不接线；以后若接入，必须用假 runner / harness 可测，且密钥不得进入 History 或证据。

父执行在 Intake 等待 `lock_scope` 之前调度该 Activity。入参只有 Intake、summary 和 `config_root`（为后续适配预留；本票确定性路径不读该目录下的密钥）。返回完整 `StoryDraft`。失败以中文错误可见地失败，且不偷偷进入 `ScopeLocked`。

## 验收与测试

启动后查询快照仍为 `Intake`，且已有 Story 草稿；缺项均标 `待证`；无臆造验收。History 中能看到 `normalize_story_draft`，且没有本票发出的 `lock_scope`。现场 History 打在已运行的官方 Temporal（`TEMPORAL_TARGET`，例如 `host.docker.internal:7233`），不起临时 Temporal 服务。
