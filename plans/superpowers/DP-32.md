## 契约

实现模块为 `dev_pipeline.evidence_contract`。[DP-24](https://weiperfect007.atlassian.net/browse/DP-24) 必须引用本契约，不另发明第二套格式。DP-24 已落地的 `evidence/verify.md` 路径、UTF-8 写入和最小字段予以保留并上收；验证分类、`render_evidence_text` / `parse_evidence_text` 与门禁仍在 `dev_pipeline.verify` / `verify_backend`。

验证证据默认写在授权 worktree 的 `evidence/verify.md`。编码为无 BOM 的 UTF-8，按字节写入，不经过控制台或 `locale.getpreferredencoding()`（Windows 上常为 cp936/GBK）。过线与失败都写。最小字段：`对应红线`、`命令或现象`、`结果`、`证据路径`，以及 `ticket_id` / `execution_id`。越界写入仍按既有沙箱拒绝，文件不得落到授权树外。

## 其他落盘

同一类证据落盘（Story Retro 当天 daily / candidate、`remote-write-rejection.md`）共享本契约的编码与写入助手，不套用验证证据的最小字段。`progress.log` 与 `heartbeat.json` 是不同产物，只共享 UTF-8 编码写入，不套用验证字段。

## 验收与测试

单元与文件系统测试证明：过线与失败文件都含最小字段；文件为无 BOM 的 UTF-8，中文与常见符号（`—` `↔` `「」`）可往返；在 `PYTHONIOENCODING=cp936` 或模拟 GBK 代码页下，助手仍写出 UTF-8 而非 GBK。Docker 内的 UTF-8 写入是必要验收，但不足以代替 Windows 抽查。Windows 抽查做法：在 Docker 中调用同一 `write_text_utf8` 助手，把文件落到宿主机目录，再用 PowerShell 的 `UTF8Encoding(false)` 按无 BOM UTF-8 解码核对，不得用系统默认代码页解读。现场 History 打在已运行的官方 Temporal（`TEMPORAL_TARGET`，例如 `host.docker.internal:7233`），覆盖既有验证过线 / 失败打回路径上的证据落盘；使用临时授权树和假 Jira，不起临时 Temporal 服务，不写真实 Jira 票，不调用现场 Cursor CLI。不 terminate 已完成的 Workflow。
